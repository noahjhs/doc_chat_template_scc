## Landing work

Background agents work on a branch in their own git worktree and land it themselves with `tools/land.sh` (run from that worktree, everything committed). It rebases onto origin/dev (on a conflict it stops and lists the files: resolve and rerun, or escalate), runs pytest (minus the two integration suites) and, if `agent/` changed, `go test ./...`, then, holding a lock so only one landing/deploy happens at a time, pushes fast-forward to origin/dev (rebasing and retesting if dev moved), deploys dev on the mini (auth, www; plus the dev Mac app, served and reinstalled on the mini, when `agent/` or `build/` changed), and starts `tools/e2e.sh` for the landed commit in the background (one e2e run at a time, on its own lock) and prints where the report will be. Escalate only for conflicts you can't resolve or decisions only the Principal can make. Never land to main or touch prod. The work board is `~/Documents/Casper-board.md`: update it when you start (In flight), land (Landed) or need a decision (Needs you).

## Background agents

Every background agent follows these conventions, so briefs can stay short:

- Finish the whole task before your final reply: if it includes an e2e run (yours or one land.sh started), wait for it to finish (poll its log or report file) and include its outcome. A detached agent's session ends at its final reply, and nobody follows up after. Shell commands time out after 10 minutes and background ones die with your session, so start the e2e run in the background and then keep polling it in the foreground (e.g. `sleep 540` between checks of its log) until it finishes; never reply while it's still running.
- **Landing.** Land code with `tools/land.sh` from your worktree. Docs-only changes: commit on dev and push (if the push is rejected: `git pull --rebase`, retry, never force). Commit messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Never touch main or prod unless the brief says so.
- **Board.** Keep `~/Documents/Casper-board.md` current (edit it with bash; the Write tool can't write in `~/Documents`): "In flight" while working, "Landed" when done, questions under "Needs you".
- **Report.** Write the full details (what changed, decisions, findings, verification) to `~/Documents/Casper-reports/<YYYY-MM-DD>-<short-slug>.md` (create the folder if needed).
- **Final reply.** At most 3 short lines: the outcome, the report file's path, and any decision needed. No lists of files, no command output, no markdown documents in the reply.
- **Launching (coordinator).** `tools/agent.sh <slug> "<brief>"` (or `@brief.md`) starts a detached agent: a separate `claude -p` in its own worktree on a fresh branch `agent/<when>-<slug>` off origin/dev, so its commands never show in the live conversation. Run it in the background; it returns when the agent is done and prints only the agent's final reply. That reply is also saved to `~/Documents/Casper-reports/logs/<when>-<slug>.log` (the full session stays under `~/.claude/projects/`). The worktree (`~/.cache/casper-agents/<when>-<slug>`) is removed once its work is on origin/dev; otherwise it is kept and its path printed.

## Architecture

**Product direction (2026-09-26 pivot):** Casper is becoming social, policy-governed host-sharing infrastructure exposed over MCP, where users bring their own agent. The built-in OpenAI conversation loop is slated for removal. Read `docs/product/` (values, trust framework, risk model, the v1 peer-backup scenario) before planning new work. The architecture below describes the code as it stands today.

Branded as **Casper** ("your friendly ghost."). Mid-refactor (2026-09): the security-rule engine, its tool-calling orchestration, and (as of the most recent round) the whole authenticated account-management surface used to live in Streamlit pages; all of that has moved server-side into `casper_service`, tested/driven via a new CLI+library harness instead of a GUI.

- **The web front end is `site/www/`** (Streamlit was retired 2026-10-08). It's served by the `casper-www` nginx container on both the `www` (public site) and `app` (signed-in) addresses. The signed-in pages are `signin`, `signup` and `guide` (Casper's guide), sharing `app.js`. The browser reaches casper_service same-origin at `/api/` (nginx proxy) and keeps its session token in localStorage. Signing in from the Mac app (which opens `<app>/signin?from=app` when nothing is paired yet) hands the session to the local daemon via a `casper://pair` link (`casper-dev://` on dev), then tells an open guide tab to carry on.
- **`agent/`** — the Go daemon ("Casper"), built via `build/build_go_macos.sh`. Runs on a user's own machine, confined to a single fixed directory (their home directory by default, computed once at startup — see `commands.Handler.HomeRoot`): pairs via a `casper://pair` URL handed off from sign-in/sign-up, reports its own confined directory and reachability to `casper_service` via presence, and is now the SOLE, authoritative decider of allow/ask/deny for every `run_shell_command` call (`commands.Handler.matchPolicy`) — `casper_service` forwards every call straight through with no local check, and the daemon returns a `Tier` verdict (`commands.Result.Tier`); an unapproved "ask" or a "deny" executes nothing, an approved "ask" resend (`commands.Request.Approved`) or an "allow" executes immediately. The daemon keeps no memory of an earlier "ask" — an approved resend is re-matched fresh every time. A separate `eval_policy` action evaluates a hypothetical call against an inline, ad hoc set of rules supplied on the request (no execution, never consulting the daemon's own cached/attached layers) — backs `casper_service`'s `POST /policies/eval`. Enforces every rule server-authoritatively regardless of what a caller might have assumed — including a rule's own `cwd` constraint and any per-argument `path_resolution` (`.`/`$PATH`/`MANPATH`), which only the daemon itself can resolve accurately (real filesystem/environment access). One daemon can be paired to more than one Casper account at once (`server.Server` holds one `commands.Handler` per paired identity, keyed by that account's own `command_key`) — each account's policy enforcement stays fully isolated even though every identity shares the same underlying machine/filesystem. Fully supersedes the old Python/PyInstaller `casper_tool.py` (deleted) on macOS; on Windows (`build/build_go_windows.sh`, `agent/cmd/casper-setup`, `docs/product/windows.md` §6) it ships as a per-user installer served at `/download/casper/windows`, unsigned until a certificate is chosen.
- **`casper_service/`** — an independently-deployed FastAPI service. Owns user accounts, hosts, Environments, and Policy Layers (named, ordered rule lists — see `db.py`'s schema and `models.py`'s `Pattern`/`PolicyLayerRuleCreateRequest` for the whitelist/blacklist/tier/`path_resolution`/`cwd` schema). `host_pairings` is keyed by `(routing_key, user_id)`, not `routing_key` alone — a physical host can be paired to several accounts simultaneously, each with its own independent credentials and policy layers. `policy.py`'s matcher (`match_policy`/`compose_policy`) is no longer used to decide anything live or mocked — it survives only for `policy.py`'s Go-parity test coverage and for `compose_policy`/`describe_rule`'s unrelated use building the model-facing tool-schema description. `POST /policies/eval` routes to a real, connected daemon (naming it via a `host` field) and asks its own `eval_policy` action to evaluate the hypothetical call — no local evaluation, no silent fallback if that daemon is unreachable. `conversations.py` + `POST /conversations/step` hold the actual OpenAI tool-calling loop: every `run_shell_command` call is forwarded straight to the daemon (`_dispatch_shell_command`), which alone decides allow/ask/deny; no streaming, host connection details resolved server-side. A `mock`/`mock_tier` pair fakes daemon/storage dispatch — mocking never evaluates policy either, `mock_tier` is the caller's own explicit, arbitrary allow/ask/deny choice. An "ask"-tier pause is persisted to a durable, per-user `pending_approvals` table (never host/device-scoped), resolvable from any of that user's own sessions (`GET`/`POST /conversations/pending-approvals*`) or, if `TELEGRAM_*` is configured and the user has linked a chat (`harness profile telegram-link`) with notifications enabled, by tapping an inline Approve/Deny button in Telegram (`POST /telegram/webhook`, secret-token-verified); resolving an "ask" resends the call to the daemon with an authorization marker rather than trusting the earlier verdict.
- **v1 platform (2026-09-28, `casper_service/mcp_server.py`, `trust.py`, `backups.py`; `agent/internal/backup`)** — the MCP front door (`/mcp`, streamable HTTP, stateless; callers authenticate with an **agent token** from `agent_tokens`, which acts on behalf of its owner), the trust framework (`relation_tuples`: mutual `friend`, `backup_peer` grants with quota and write tier; `offerings`, `access_requests`, `friend_requests`), and peer backup. Friend requests, access requests, backup writes and MCP shell-command asks are all rows in the generalized `pending_approvals` (`kind`/`payload`/`requester_user_id`; handlers in `main.py`'s `_APPROVAL_HANDLERS`), so the approver can be someone other than the requester. The daemon encrypts (age) and signs (ed25519) on the owner's machine. On the peer, it decides every chunk write fresh from grants it fetches itself (`GET /hosts/grants`); `casper_service` only relays ciphertext. `agent/cmd/casper-testdaemon` is a headless, test-only daemon that `tests/test_backup_integration.py` drives through a real `casper_service`.
- **Master key (recovery v2 P2, 2026-10-16; `agent/internal/recovery`)** — each paired identity has one 32-byte master key in the login Keychain (`Casper Master Key`, made by `mirrord.Service.Step` the first time a Mac that owns folders reconciles, never on a restoring Mac). New folders (`mirror_folders.key_scheme = 'derived1'`) get their Syncthing password by HKDF from it, so nothing per-folder is stored; folders from before keep their random password (`'legacy'`), frozen into a bundle sealed under a key derived from the master key and kept by casper_service as ciphertext (`legacy_bundles`, `PUT/GET /hosts/legacy-bundle`, write-once). Kit v3 holds the master key (plus the legacy plaintext), so it never goes stale; v2 kits still import. Design: `docs/product/recovery-v2-design.md`.
- **Agent onboarding (2026-09-30)** — a person's own agent sets Casper up for them: `onboarding/AGENTS.md` (a short bootstrap: install, account, pair, connect, restart) is served with the deployment's URL filled in at `/agents.md` and `/onboarding.zip`. Everything after that (the voice, the rules, how to invite/mirror/undo) is in the MCP server's `instructions` (`mcp_server.py`'s `INSTRUCTIONS`/`VOICE`), which agents receive silently on connect: no visible instruction files, and an agent that seems to just know (2026-10-06, after the first invited-user walkthrough; the guide shares `VOICE`). the app is downloadable at `/download/casper/macos` (all `Cache-Control: no-store` — Cloudflare caches `.zip` URLs). Mechanics live in `Casper setup <command>` (`agent/internal/setup`, built into the app binary: status/account/pair/agent/notifications/recovery-kit). MCP adds the `my_casper` ledger, invites (`create_invite`/`redeem_invite`), `publish_offering`, `list_approvals`/`decide_approval` (others' requests only — Rule of Two) and `revoke`; sharing tools default to `preview=true`. Principles: `docs/product/agent-first-ux.md`.
- **Mirroring with history (2026-10-01; the v1 product, replacing snapshot backup)** — Syncthing is bundled in Casper.app and run privately by `agent/internal/mirror` (declarative `Desired` state; protection status; catcher staging; history pruning; version restore via Syncthing's own exported crypto functions), glued by `agent/internal/mirrord`. `casper_service/mirroring.py` is discovery and computes each Mac's desired state from grants (`mirror_peer`/`catcher_peer`). It also handles consent (`mirror_consent`, answered only outside the agent: the native dialog → `/hosts/consent`, or Telegram), status and nudges, and Casper's own catcher (the `catcher` Syncthing container, the last resort). Data moves only peer to peer. Design: `docs/product/scenarios/mirroring.md`. Carve-outs and honesty (2026-10-16): `*.photoslibrary` is left out of every mirrored folder (Syncthing ignore, `mirror/carveout.go`), and a folder with items Syncthing can't read (`unreadable_items` in its status) is never reported protected (`_status_text`, the guide's `unreadable` step).
- **Restore (2026-10-16; `casper_service/restore.py`, `main.py`'s `_mcp_restore_*`, `agent/internal/mirror/restore.go`)** — file restore driven by an agent or the guide, with feature parity and no standing app GUI (`docs/product/restore-design.md`): `list_versions` (incl. `deleted_only`), `restore_version` (a file, as a dated copy next to the original), `restore_as_of` (folders as of a time, as new dated sibling folders), `show_restore_picker` (the guide draws it inline on the page via `GET /restore/picker` + `POST /restore/pick`; a person's own agent asks the Mac for a native list, answered on `POST /hosts/restore-picked`). Copy is the default and needs no confirmation; `mode='replace'` only when a copy doesn't fit the disk (the daemon reports free space via `mirror_restore_plan`) and on the person's yes.
- **Casper's guide (2026-10-02)** — the onboarding agent for people without one: `casper_service/guide.py`, a tool-calling loop over the same functions as the MCP server, on a Nous Portal model (`NOUS_API_KEY`, `GUIDE_MODEL`; chosen by `tests/guide_eval.py`, which runs scripted conversations against candidate models and is run by hand because it uses the paid API). It's served on the web (`pages/guide.py`, `/guide/message`, `/guide/history`) and in Telegram (plain messages from a linked chat), sharing one conversation per person (`guide_messages`). It's **gated** (2026-10-11): `guide.stage_for(Facts, history)` picks one current setup step from Casper's own state (`main._guide_facts`): accept invite, install, choose folder, consent, first copy, recovery kit (reported by the app via `POST /profile/recovery-kit`), give back, then open. Each turn gets only that step's instruction (NOW) and tools, plus the read-only ones. When a scripted step begins, Casper writes its line, not the model. Its buttons come from the step. Syncthing traffic that can't go direct uses Casper's own relay (`st-relay` container on port 22067). The home router forwards that port: `casper_service` keeps it open with NAT-PMP (`ST_RELAY_NATPMP_GATEWAY`, `ST_RELAY_PUBLIC_PORT`, `ST_RELAY_ID`) and hands Macs the router's current public address (`mirroring.relays()`). Tailscale Funnel can't carry relay sessions, since it routes by TLS name and relay sessions send none; see `tools/relaycheck`, which tests any relay end to end.
- **`site/www/`** — the public site ("Warm Paper", chosen 2026-10-02): static landing, `/download` and `/invite#CODE` pages plus the signed-in pages above, served by the `casper-www` nginx container (`docker-compose.yml`'s `www`; each deployment's URLs are filled in at start). On dev, cloudflared sends both `dev-www` and `dev-app` to `casper-www:8080`; prod still runs Streamlit (`casper-app-prod`) until promotion, which needs the www container and those routes. An accepted invite stays usable until the friend's first mirror runs (`invites.completed_at`), so someone starting over can reuse it. The invite page reads the public, rate-limited `GET /invites/info`, and its no-agent path carries the code through `signup?invite=` into the guide. Invite messages link it when `PUBLIC_WWW_URL` is set. Invites are personal (2026-10-05): they greet the invitee by name (`for_whom`) into the inviter's named **group** (`groups` table; redeeming adds a `member` tuple), and can be delivered by email (`casper_service/mailer.py`, plain SMTP via `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASSWORD`/`MAIL_FROM`) and/or as a forwardable copy with a Share button in the inviter's own Telegram (a bot can't message strangers). "Begin setup with Casper's guide" links to `signup?start=guide`, which skips the pairing hand-off and goes straight to the guide.
- **Test scenarios (`tools/scenario.py`, `tools/scenarios.toml`)** — walkthroughs run on local macOS VMs (Tart), one per persona (riley = inviter with Claude Code, noah = invitee). `tools/scenario.py start invite` prepares this Mac (stops other VMs, frees memory), then resets each persona to a named checkpoint: it clones the VM from a local snapshot (`noah-base`, `noah-base-claude`, `riley-base`; these hold only local Mac state). `tools/scenario.py copy|rename|delete|edit|save|show` manage snapshots and the config together, deletes the persona's dev account, and replays steps (install Casper, account, pair, connect Claude, publish an offering…). Steps run in the VM through `tart exec` and on the server through dev-only endpoints (`casper_service/devtools.py`, which exist only when `DEV_ADMIN_TOKEN` is set, never on prod). New checkpoints are recipes in the TOML; a checkpoint with `extends` builds on another. `capture <checkpoint|scenario>` saves a checkpoint as it is right now, so hand tweaks are kept. It holds the VM (snapshot `cp-<checkpoint>`) plus that persona's server rows, exported while the VM is off (devtools' `_selectors` is the one definition used for deletion and export). After that, `reset` restores the capture (refreshing the Casper app) instead of replaying. `start|reset <name> --vnc` serves each VM's screen over VNC instead of opening its window, and `tools/vmgui.py` (`shot`/`click`/`type`/`key`/`open`) then looks at and drives it from outside, with no permissions inside the VM; that's how Claude runs GUI end-to-end tests. Riley's Claude can be driven without a window too: `tart exec riley-mac … claude -p "…"`. **Windows (2026-10-16, `tools/winvm.py`, `docs/product/windows.md` §9):** persona `noah-windows`/scenario `windows` is a Windows 11 ARM VM on headless QEMU (HVF), screen on VNC (`vmgui.py … windows`), commands over OpenSSH (`scenario.py exec noah-windows "<powershell>"`), clean snapshot `windows-base`, holding the e2e lock while it runs (`tools/e2e.sh` exports `CASPER_E2E_LOCK_HELD`); `winvm.py utm` makes a separate UTM copy for hands-on testing.
- **Unattended end-to-end runs (2026-10-12)** — `tools/e2e.sh [scenario] [commit]` deploys the commit to the **test stack** and has a background `claude -p` follow `.claude/skills/e2e-run` in its own worktree, writing a report to `~/Documents/Casper e2e runs/<when>/`. The test stack (`tools/test_stack.sh setup|deploy|status|down`) is a third deployment on the mini next to dev and prod. It has its own checkout pinned to the commit, `casper-*-test` containers (one parameterized `docker-compose.yml`; it starts only www/auth/catcher/relay and shares dev's Syncthing relay), database, catcher and `test-*` addresses, plus a `DEPLOY_ENV=test` app ("Casper Test", `casper-test://`, `Casper-test` config directory). It keeps email instead of sending it (`MAIL_SINK`, read with `GET /dev/mail` or `tools/scenario.py mail`) and has no Telegram, so runs reach nobody. `tools/scenario.py … --env test` targets it. Runs use one VM: Riley is a **headless persona** (`headless = true`, scenario `invite-headless`), meaning `casper-testdaemon` plus Syncthing on the mini, joined to the relay and reporting presence (`-relay-domain`), with an agent that's a clean Claude Code holding only Casper's tools (`tools/scenario.py ask riley-headless "…"`).
- **`relay/`** — a separate Go tunneling service (not the agent, not casper_service).
- **`harness/`** — a standalone package (own `pyproject.toml`) driving `casper_service`'s HTTP API directly: `harness/client.py` (plain functions, no CLI dependency) plus a Typer CLI (`harness/cli.py`). The primary way the security-rule engine gets tested and iterated on now — `harness eval --host <host>` (routes to a real daemon) → `harness call-tool [--mock] [--mock-tier allow|ask|deny]` (one live/mocked tool call) → `harness chat [--mock] [--mock-tier ...]` (a real conversational turn). Also does YAML policy-layer authoring (`harness policy apply <file.yaml>`); account/host/Environment/profile management (`harness signup`/`login`, `harness pair`, `harness hosts`/`environment`/`profile` — full parity with what `pages/environments.py`/`settings_*.py` used to do); scripting a REAL daemon's pairing (`harness pair-daemon`, macOS-only, manual-verification-only — fires the same `casper://pair` Apple Event a browser sign-in click would); and checking/answering pending "ask"-tier approvals (`harness approvals list`/`respond` — a durable, per-user queue any of the account's own sessions can resolve, not a designated "attended" machine — see `casper_service`'s `pending_approvals` table).

`casper_service` reads `OPENAI_API_KEY` from its own process environment (shared via `.env`/`env_file` in `docker-compose.yml`) since it now makes its own OpenAI calls. Telegram-based approvals (see above) similarly need `TELEGRAM_BOT_TOKEN`/`TELEGRAM_BOT_USERNAME`/`TELEGRAM_WEBHOOK_SECRET` in that same environment, plus a real Telegram bot (via @BotFather, free) whose webhook is registered (`setWebhook`) to point at this deployment's `/telegram/webhook` with that same secret -- all optional (a deployment without them simply never sends/accepts approvals this way, same as the OpenAI key being required only for real, non-mock conversation steps). Unlike Twilio, this needs no per-message cost or phone number.
