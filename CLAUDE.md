## Architecture

**Product direction (2026-09-26 pivot):** Casper is becoming social, policy-governed host-sharing infrastructure exposed over MCP, where users bring their own agent. The built-in OpenAI conversation loop is slated for removal. Read `docs/product/` (values, trust framework, risk model, the v1 peer-backup scenario) before planning new work. The architecture below describes the code as it stands today.

Branded as **Casper** ("your friendly ghost.", see `utils/branding.py`). Mid-refactor (2026-09): the security-rule engine, its tool-calling orchestration, and (as of the most recent round) the whole authenticated account-management surface used to live in Streamlit pages; all of that has moved server-side into `casper_service`, tested/driven via a new CLI+library harness instead of a GUI.

- **`casper_app.py`** + **`pages/download.py`** (public, unauthenticated, `www` subdomain, gated by `require_www_subdomain()`) + **`pages/signin.py`**/**`pages/signup.py`** (`app` subdomain, gated by `require_app_subdomain()`) — what's left of the Streamlit app: a real end user downloads the agent binary, signs in or signs up, and that fires the `casper://pair` hand-off to their local daemon (see `utils/auth.py`'s `build_pair_url`/`login_with_auth_service`/`signup_with_auth_service`, `utils/browser_nav.py`'s `click_anchor_js` for how a custom-scheme URL actually dispatches from inside Streamlit's sandboxed iframe). That's the entire remaining surface, deliberately trimmed from what it used to be — no chat, no policy-authoring, no Environments/Settings UI, and there's still no product-facing way for a user to confirm pairing actually succeeded (see `docs/user-flows/first-time-setup.md`'s Known Issues) — account/host/Environment/profile *management* (as opposed to the one-time act of signing in) all moved to the harness (see below).
- **`agent/`** — the Go daemon ("Casper"), built via `build/build_go_macos.sh`. Runs on a user's own machine, confined to a single fixed directory (their home directory by default, computed once at startup — see `commands.Handler.HomeRoot`): pairs via a `casper://pair` URL handed off from sign-in/sign-up, reports its own confined directory and reachability to `casper_service` via presence, and is now the SOLE, authoritative decider of allow/ask/deny for every `run_shell_command` call (`commands.Handler.matchPolicy`) — `casper_service` forwards every call straight through with no local check, and the daemon returns a `Tier` verdict (`commands.Result.Tier`); an unapproved "ask" or a "deny" executes nothing, an approved "ask" resend (`commands.Request.Approved`) or an "allow" executes immediately. The daemon keeps no memory of an earlier "ask" — an approved resend is re-matched fresh every time. A separate `eval_policy` action evaluates a hypothetical call against an inline, ad hoc set of rules supplied on the request (no execution, never consulting the daemon's own cached/attached layers) — backs `casper_service`'s `POST /policies/eval`. Enforces every rule server-authoritatively regardless of what a caller might have assumed — including a rule's own `cwd` constraint and any per-argument `path_resolution` (`.`/`$PATH`/`MANPATH`), which only the daemon itself can resolve accurately (real filesystem/environment access). One daemon can be paired to more than one Casper account at once (`server.Server` holds one `commands.Handler` per paired identity, keyed by that account's own `command_key`) — each account's policy enforcement stays fully isolated even though every identity shares the same underlying machine/filesystem. Fully supersedes the old Python/PyInstaller `casper_tool.py` (deleted) on macOS; no Windows build pipeline exists yet even though the agent's own source has Windows-specific files.
- **`casper_service/`** — an independently-deployed FastAPI service. Owns user accounts, hosts, Environments, and Policy Layers (named, ordered rule lists — see `db.py`'s schema and `models.py`'s `Pattern`/`PolicyLayerRuleCreateRequest` for the whitelist/blacklist/tier/`path_resolution`/`cwd` schema). `host_pairings` is keyed by `(routing_key, user_id)`, not `routing_key` alone — a physical host can be paired to several accounts simultaneously, each with its own independent credentials and policy layers. `policy.py`'s matcher (`match_policy`/`compose_policy`) is no longer used to decide anything live or mocked — it survives only for `policy.py`'s Go-parity test coverage and for `compose_policy`/`describe_rule`'s unrelated use building the model-facing tool-schema description. `POST /policies/eval` routes to a real, connected daemon (naming it via a `host` field) and asks its own `eval_policy` action to evaluate the hypothetical call — no local evaluation, no silent fallback if that daemon is unreachable. `conversations.py` + `POST /conversations/step` hold the actual OpenAI tool-calling loop: every `run_shell_command` call is forwarded straight to the daemon (`_dispatch_shell_command`), which alone decides allow/ask/deny; no streaming, host connection details resolved server-side. A `mock`/`mock_tier` pair fakes daemon/storage dispatch — mocking never evaluates policy either, `mock_tier` is the caller's own explicit, arbitrary allow/ask/deny choice. An "ask"-tier pause is persisted to a durable, per-user `pending_approvals` table (never host/device-scoped), resolvable from any of that user's own sessions (`GET`/`POST /conversations/pending-approvals*`) or, if `TELEGRAM_*` is configured and the user has linked a chat (`harness profile telegram-link`) with notifications enabled, by tapping an inline Approve/Deny button in Telegram (`POST /telegram/webhook`, secret-token-verified); resolving an "ask" resends the call to the daemon with an authorization marker rather than trusting the earlier verdict.
- **v1 platform (2026-09-28, `casper_service/mcp_server.py`, `trust.py`, `backups.py`; `agent/internal/backup`)** — the MCP front door (`/mcp`, streamable HTTP, stateless; callers authenticate with an **agent token** from `agent_tokens`, which acts on behalf of its owner), the trust framework (`relation_tuples`: mutual `friend`, `backup_peer` grants with quota and write tier; `offerings`, `access_requests`, `friend_requests`), and peer backup. Friend requests, access requests, backup writes and MCP shell-command asks are all rows in the generalized `pending_approvals` (`kind`/`payload`/`requester_user_id`; handlers in `main.py`'s `_APPROVAL_HANDLERS`), so the approver can be someone other than the requester. The daemon encrypts (age) and signs (ed25519) on the owner's machine. On the peer, it decides every chunk write fresh from grants it fetches itself (`GET /hosts/grants`); `casper_service` only relays ciphertext. `agent/cmd/casper-testdaemon` is a headless, test-only daemon that `tests/test_backup_integration.py` drives through a real `casper_service`.
- **Agent onboarding (2026-09-30)** — a person's own agent sets Casper up for them: `onboarding/AGENTS.md` (a short bootstrap: install, account, pair, connect, restart) is served with the deployment's URL filled in at `/agents.md` and `/onboarding.zip`. Everything after that (the voice, the rules, how to invite/mirror/undo) is in the MCP server's `instructions` (`mcp_server.py`'s `INSTRUCTIONS`/`VOICE`), which agents receive silently on connect: no visible instruction files, and an agent that seems to just know (2026-10-06, after the first invited-user walkthrough; the guide shares `VOICE`). the app is downloadable at `/download/casper/macos` (all `Cache-Control: no-store` — Cloudflare caches `.zip` URLs). Mechanics live in `Casper setup <command>` (`agent/internal/setup`, built into the app binary: status/account/pair/agent/notifications/recovery-kit). MCP adds the `my_casper` ledger, invites (`create_invite`/`redeem_invite`), `publish_offering`, `list_approvals`/`decide_approval` (others' requests only — Rule of Two) and `revoke`; sharing tools default to `preview=true`. Principles: `docs/product/agent-first-ux.md`.
- **Mirroring with history (2026-10-01; the v1 product, replacing snapshot backup)** — Syncthing is bundled in Casper.app and run privately by `agent/internal/mirror` (declarative `Desired` state; protection status; catcher staging; history pruning; version restore via Syncthing's own exported crypto functions), glued by `agent/internal/mirrord`. `casper_service/mirroring.py` is discovery and computes each Mac's desired state from grants (`mirror_peer`/`catcher_peer`). It also handles consent (`mirror_consent`, answered only outside the agent: the native dialog → `/hosts/consent`, or Telegram), status and nudges, and Casper's own catcher (the `catcher` Syncthing container, the last resort). Data moves only peer to peer. Design: `docs/product/scenarios/mirroring.md`.
- **Casper's guide (2026-10-02)** — the onboarding agent for people without one: `casper_service/guide.py`, a tool-calling loop over the same functions as the MCP server, on a Nous Portal model (`NOUS_API_KEY`, `GUIDE_MODEL`; chosen by `tests/guide_eval.py`, which runs scripted conversations against candidate models and is run by hand because it uses the paid API). It's served on the web (`pages/guide.py`, `/guide/message`, `/guide/history`) and in Telegram (plain messages from a linked chat), sharing one conversation per person (`guide_messages`). Syncthing traffic that can't go direct uses Casper's own relay (`st-relay` container, published via Tailscale Funnel on port 10000; `ST_RELAY_URL`).
- **`site/www/`** — the public site ("Warm Paper", chosen 2026-10-02): static landing, `/download` and `/invite#CODE` pages, served by the `casper-www` nginx container (`docker-compose.yml`'s `www`; each deployment's URLs are filled in at start). It replaces the Streamlit `www` pages on dev (cloudflared `dev-www` → `casper-www:8080`); prod's `www` still points at Streamlit until promotion. The invite page reads the public, rate-limited `GET /invites/info`, and its no-agent path carries the code through `signup?invite=` into the guide. Invite messages link it when `PUBLIC_WWW_URL` is set. Invites are personal (2026-10-05): they greet the invitee by name (`for_whom`) into the inviter's named **group** (`groups` table; redeeming adds a `member` tuple), and can be delivered by email (`casper_service/mailer.py`, plain SMTP via `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASSWORD`/`MAIL_FROM`) and/or as a forwardable copy with a Share button in the inviter's own Telegram (a bot can't message strangers). "Begin setup with Casper's guide" links to `signup?start=guide`, which skips the pairing hand-off and goes straight to the guide.
- **`relay/`** — a separate Go tunneling service (not the agent, not casper_service).
- **`harness/`** — a standalone package (own `pyproject.toml`) driving `casper_service`'s HTTP API directly: `harness/client.py` (plain functions, no CLI dependency) plus a Typer CLI (`harness/cli.py`). The primary way the security-rule engine gets tested and iterated on now — `harness eval --host <host>` (routes to a real daemon) → `harness call-tool [--mock] [--mock-tier allow|ask|deny]` (one live/mocked tool call) → `harness chat [--mock] [--mock-tier ...]` (a real conversational turn). Also does YAML policy-layer authoring (`harness policy apply <file.yaml>`); account/host/Environment/profile management (`harness signup`/`login`, `harness pair`, `harness hosts`/`environment`/`profile` — full parity with what `pages/environments.py`/`settings_*.py` used to do); scripting a REAL daemon's pairing (`harness pair-daemon`, macOS-only, manual-verification-only — fires the same `casper://pair` Apple Event a browser sign-in click would); and checking/answering pending "ask"-tier approvals (`harness approvals list`/`respond` — a durable, per-user queue any of the account's own sessions can resolve, not a designated "attended" machine — see `casper_service`'s `pending_approvals` table).

The OpenAI API key and the auth service's domain (`AUTH_SERVICE_DOMAIN`) are read from `.streamlit/secrets.toml` via `st.secrets` in the Streamlit app; `casper_service` reads `OPENAI_API_KEY` from its own process environment (shared via `.env`/`env_file` in `docker-compose.yml`) since it now makes its own OpenAI calls. Telegram-based approvals (see above) similarly need `TELEGRAM_BOT_TOKEN`/`TELEGRAM_BOT_USERNAME`/`TELEGRAM_WEBHOOK_SECRET` in that same environment, plus a real Telegram bot (via @BotFather, free) whose webhook is registered (`setWebhook`) to point at this deployment's `/telegram/webhook` with that same secret -- all optional (a deployment without them simply never sends/accepts approvals this way, same as the OpenAI key being required only for real, non-mock conversation steps). Unlike Twilio, this needs no per-message cost or phone number.
